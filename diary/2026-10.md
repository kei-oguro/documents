Dependency Injection がピンと来ない。共通の問題意識はあるが、正確な輪郭、何が興味の内で何が外なのかが判然としない。どこからでもアクセスできる素朴な Singleton はダメだ。そういう意味では、どこからでも `Resolve<T>()` するのはダメだ。そこで LifetimeScope がある。そのスコープに対して `Resolve<T>()` するのはどうなんだ？もちろん、コンストラクタインジェクションされるのがベストであって Resolve() すべきでないというのが DI。個人的には、どのスコープがどのオブジェクトを提供できるのかを、実行時ではなくコンパイル時にチェックできるように、スコープごとにクラスを作って、プロパティでサービスを提供するような、サービスロケータを細かい単位で用意するようなのが妥協できる Singleton のグローバルっぽさへの対処ではないかと思う。AI に相談してみるか。

その細かな単位のサービスロケータで提供するプロパティは interface を返すべきだ。そこは DI と興味を共有していると思う。ここで言う細かな単位のサービスロケータ自体も interface を切って提供することでユニットテストのモックがやりやすくなるかも知れない。個人的には、これまでに経験したプロジェクトでの DI の使い方が、有効な LifetimeScope が static で提供されるような環境だった。これはそれらのプロジェクトでの妥協だったのか、DI の興味が Dynamic Context 的なところにあるのか、どうなんだろう。

    ```csharp
    public static string BuildPath(Transform t) {
      return Build(new StringBuilder($"[{t.gameObject.scene.name}] "), t)

      static StringBuilder Build(StringBuilder sb, Transform t) { // Recursive call
        if (t.parent != null) {
          Build(sb, t.parent);
    ```

    ```csharp
      return $"[{transform.gameObject.scene.name}] " + string.Join("/", Build2(transform));

      IEnumerable<string> Build2(Transform t) { // yield return with recursive call
        foreach (var s in t.parent != null ? Build2(t.parent) : Array.Empty<string>()) {
          yield return s;
        }

        yield return t.name;
      }
    }
    ```

    ```csharp
      IEnumerable<string> Build3(Transform startNode) { // from tail to head sequence
        for (var t = startNode; t != null; t = t.parent) {
    ```
